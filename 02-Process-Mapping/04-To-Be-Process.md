# To-Be Process

## Purpose

This document describes the proposed future-state process for receiving, recording, managing and resolving student support requests at Cape Learning Institute (CLI).

The To-Be process is designed to address the problems identified in the current As-Is process and improve request capture, assignment, tracking, communication, monitoring and reporting.

The process represents a proposed future state for this fictional case study and does not describe an implemented system.

## Process Scope

### Process Start

The process begins when a student submits a support request through the proposed centralised student support system.

### Process End

The process ends when the student's request has been resolved, the outcome has been recorded and the request has been closed.

## Process Actors

The main actors involved in the future-state process are:

- Student
- Support Staff
- Support Manager
- Academic / Faculty Staff, where academic assistance is required
- IT / System Administrator

## Process Inputs

The main inputs to the future-state process include:

- Student details
- Support request
- Request description
- Request category
- Supporting information or documents
- Request priority
- Staff information
- Request status
- Referral information, where required

## To-Be Process Flow

The proposed future-state process can be summarised as follows:

1. **Student identifies a problem**
   - The student requires assistance from the Student Support Department.

2. **Student submits a support request**
   - The student submits the request through the centralised student support system.

3. **System records the request**
   - The system captures the submitted information and generates a unique request reference number.

4. **Student receives confirmation**
   - The student receives confirmation that the request has been submitted successfully.

5. **Support staff reviews the request**
   - Support staff checks the request to determine whether sufficient information has been provided.

6. **Is sufficient information available?**
   - **No:** The student is contacted and asked to provide the missing information.
   - **Yes:** The request continues to the next stage.

7. **Request is categorised and prioritised**
   - The request is assigned a suitable category and priority level.

8. **Request is assigned**
   - The request is allocated to the appropriate support staff member.

9. **Request status is updated**
   - The request status is updated to indicate that it has been assigned or is in progress.

10. **Staff member investigates the request**
    - The responsible staff member investigates the issue and takes the required action.

11. **Is additional assistance required?**
    - **Yes:** The request is referred to the appropriate department or staff member, and the referral is recorded and tracked.
    - **No:** The staff member continues towards resolving the request.

12. **Request is resolved**
    - The student's issue is addressed and the outcome is recorded.

13. **Student receives a response**
    - The student is informed of the outcome or resolution.

14. **Request is closed**
    - The completed request is closed and the final information is retained.

15. **Management information is updated**
    - The structured request information becomes available for monitoring and management reporting.

16. **END**
    - The student support request process is complete.

## Future Process Description

### 1. Request Submission

The student submits a support request through a centralised system.

The request form should capture the information required to understand and process the request, including student details, request category, description and supporting information where applicable.

### 2. Request Recording

The system records the request and generates a unique reference number.

The reference number allows the request to be identified and tracked throughout the process.

### 3. Request Confirmation

The student receives confirmation that the request has been successfully submitted.

The confirmation should include the request reference number so that the student can refer to the request when communicating with Student Support.

### 4. Request Review

Support staff review the submitted request to determine whether sufficient information has been provided.

If information is missing, the student is contacted and the request is placed into an appropriate status until the required information is received.

### 5. Categorisation and Prioritisation

The request is assigned a category based on the type of assistance required.

The request is also prioritised according to its urgency and potential impact.

This helps support staff determine which requests require attention first.

### 6. Request Assignment

The request is assigned to the appropriate support staff member.

The assigned staff member becomes responsible for progressing the request and updating its status.

### 7. Request Handling

The responsible staff member investigates the request and takes the required action.

The request status is updated as work progresses so that its current position can be monitored.

### 8. Referral

If additional assistance is required, the request is referred to the appropriate department or staff member.

The referral is recorded so that responsibility and progress can be tracked.

### 9. Resolution

Once the student's issue has been addressed, the staff member records the outcome of the request.

The student is informed of the resolution.

### 10. Request Closure

After the request has been resolved, the request is closed.

The final request information is retained as part of the support record.

### 11. Management Monitoring

Structured request information can be used to provide management with information about request volumes, staff workload, outstanding requests, overdue requests, response times and resolution times.

## Proposed Request Statuses

The future-state process should use standardised statuses to improve visibility and consistency.

Possible statuses include:

- New
- Assigned
- In Progress
- Awaiting Information
- Referred
- Resolved
- Closed

Using defined statuses allows staff and management to understand the current position of each request more easily.

## Expected Process Improvements

The proposed To-Be process is intended to address the main problems identified in the current As-Is process.

| Current Problem | Proposed Improvement | Expected Benefit |
|---|---|---|
| Multiple communication channels | Centralised request submission | More consistent request capture |
| Manual request recording | Structured digital request capture | Reduced manual data entry |
| Duplicate requests | Unique request reference numbers | Easier identification and tracking |
| Unclear responsibility | Clear request assignment | Improved ownership |
| Manual status tracking | Standardised request statuses | Better visibility of progress |
| Difficulty identifying overdue requests | Request monitoring and alerts | Faster identification of delays |
| Department referral delays | Recorded and trackable referrals | Improved handover and accountability |
| Manual reporting | Structured management information | More efficient reporting |

- Standardised request information.
- Unique request reference numbers.
- Request categorisation.
- Request prioritisation.
- Clear request ownership.
- Standardised request statuses.
- Request tracking.
- Referral tracking.
- Visibility of outstanding and overdue requests.
- Management reporting.
- Controlled access to student information.

The To-Be process therefore provides a practical link between the identified business problems, requirements and proposed process improvements.

## Expected Business Outcomes

If implemented, the proposed future-state process could help CLI to:

- Improve the consistency of student support request capture.
- Reduce manual administration.
- Improve request ownership and accountability.
- Improve visibility of request progress.
- Reduce the risk of requests being overlooked.
- Improve monitoring of outstanding and overdue requests.
- Improve communication with students.
- Improve the tracking of departmental referrals.
- Provide more reliable information for management reporting.
- Support more efficient student support operations.

These outcomes are expected benefits of the proposed process and are not claims that the improvements have already been achieved.
